SoundRouter

A native macOS app (Swift, SwiftUI, Core Audio) that sends each app's audio to the output you choose, plays input devices like an iPad through any output, and switches things automatically when devices come and go. It replaces the Audio MIDI Setup + LadioCast routine and covers the core SoundSource features.

Per-app routing

Chrome → Speakers, Music → Headset, at the same time, each with its own volume up to 400%.

Input play-through

iPad, mic, interface or capture card → any output, no LadioCast. One switch enables the iPad.

Rules & fallbacks

Priority lists and triggers. When a device is missing: alert, alert and use another device, or alert and silence.

SoundSource-style effects

Boost, balance, Magic Boost, a 10-band EQ, headphone EQ per device, and any Audio Unit plug-in.

Menu bar + window

Full window for setup and a compact menu bar panel for everyday use. Can hide the Dock icon.

Always on

Starts at login, relaunches if it crashes, and includes a privileged helper that restarts Core Audio.

No virtual audio driver is installed. Per-app capture uses Apple's Core Audio process taps (CATapDescription, macOS 14.2+), and this project targets macOS 27.

Build & run

The repo includes SoundRouter.xcodeproj. Its source folders are synchronized groups, so new files under Sources/App, Sources/Shared or Sources/Helper are picked up without editing the project.

The app icon is an Icon Composer file, Sources/App/Resources/AppIcon.icon (open it with Xcode › Open Developer Tool › Icon Composer). The menu bar icon and accent color are in Sources/App/Resources/Assets.xcassets.

cd SoundRouter
open SoundRouter.xcodeproj
# or from the command line:
xcodebuild -project SoundRouter.xcodeproj -scheme SoundRouter build
  1. In Xcode, select the SoundRouter target → Signing & Capabilities and pick your team. Do the same for SoundRouterHelper. Without a team, it builds ad-hoc signed ("Sign to Run Locally"), which is enough to compile but not for the helper daemon or login items.
  2. If you change the bundle ID, keep the helper's ID as <app id>.Helper. The helper uses it to verify that only this app can call it.
  3. Build and run with ⌘R. For a real install, use Product › Archive, export a Developer ID-signed copy, and put it in /Applications. Login items and the helper daemon work best from /Applications.
TargetWhat it is
SoundRouterThe app: window, menu bar extra, audio engine. It isn't sandboxed and has the hardened runtime and audio-input entitlement.

Per-app routing

Open the Apps page. Every app that uses audio is listed with a level meter, a volume slider (0–400%), mute, and an output menu.

Chrome→process tap (original muted)→effects→MacBook Speakers
Music→process tap (original muted)→effects→Headset
  • Quick: pick an output from the row's menu.
  • Priority list: click ⚙︎ (the sliders icon) and add several outputs in order, e.g. Headset → AirPods → Speakers. The app always uses the first one that's connected and moves back when a higher one reconnects.
  • Play on all: send one app to several outputs at once.
  • Apps not running yet: use Add App in the toolbar to create a route in advance. It applies as soon as the app makes sound.
  • Helper processes (Chrome's renderer, Safari's WebContent) are grouped under their app automatically.
  • An app left on System Default at 100% with no effects isn't touched at all, so it adds no latency.

iPad & input play-through

This replaces the old routine: Audio MIDI Setup → Enable iPad → LadioCast → Headset.

  1. On Inputs, turn on Enable iPad & iPhone audio. This does what “Enable” in Audio MIDI Setup does: it sets kCMIOHardwarePropertyAllowScreenCaptureDevices.
  2. Connect the iPad with a cable, unlock it, and tap Trust if asked. It appears in the list.
  3. Click Play Through…, choose the output (e.g. Headset), and optionally add fallbacks, volume and EQ.

From then on, the route starts by itself whenever the iPad is plugged in and stops when it's unplugged. Any other input works the same way: mics, interfaces, capture cards, even a specific channel pair of a multichannel interface.

For the lowest latency, match sample rates (Tools › Match sample rates) and use a smaller buffer on the output device (Devices › Buffer size).

Rules, priority & fallbacks

Fallback when an output is missing (per route)

OptionWhat happens
Use another devicePlays on the fallback device you pick (or the system default) until a preferred one returns
SilenceThe app is muted until a preferred output returns
Leave on current outputSoundRouter steps aside and macOS plays it as usual
Show an alertWorks with any of the above. You get a notification when the route falls back and when it's restored.

Device priority (per profile)

Ordered lists of preferred default output and input devices. When devices connect or disconnect, the highest connected one becomes the system default.

Rules (global)

Triggers: device connects or disconnects, app launches or quits. Actions: set default output, input or sound-effects device, set a device's volume, switch profile, turn an app or input route on or off, show a notification. Example: when “Headset” connects → switch to profile “Headphones”.

Profiles

Each profile holds its own app routes, input routes and device priority, e.g. “Desk”, “Headphones only”, “Streaming”. Switch from the toolbar, the menu bar, a rule, or ⌃⌥⌘P.

Volume boost, EQ & effects

Every app route, input route and output device has the same effect chain, processed in this order:

10-band EQ→Magic Boost→Audio Units→Volume & balance→output-device chain→limiter
  • Volume up to 400%, with a peak limiter at the end so boosted audio doesn't clip.
  • Magic Boost: a compressor plus makeup gain that lifts quiet dialogue.
  • EQ: 32 Hz – 16 kHz, ±12 dB, with built-in presets (Bass Boost, Voice, Loudness, Headphones…) and your own saved presets.
  • Audio Units: add any installed effect (Apple's AUReverb, AUDelay, AUDynamicsProcessor, or third-party plug-ins), reorder or bypass them, and open their editor. Settings are saved with the route.
  • Headphone EQ: set EQ on an output device (Devices page) and it applies wherever that device is used. Turn on Settings › Process all audio to apply it to apps without routes too.
  • Software volume for HDMI and USB devices that macOS can't control, either from the menu bar or with the volume keys (Settings).

Menu bar & always-on

SettingMechanism
Start at loginSMAppService.mainApp
Always onSMAppService.agent with app.soundrouter.keepalive.plist (KeepAlive.SuccessfulExit = false). It relaunches after a crash but not after you choose Quit.
Show in DockSwitches between .regular and .accessory activation policy. The menu bar icon is always shown.

Closing the window keeps SoundRouter running in the menu bar. When it quits, every tap is removed and apps go back to normal output immediately. Taps and aggregates are private to the process, so the system cleans them up even after a crash.

Tools

  • Restart Core Audio: through the helper if it's installed (no password), otherwise through an administrator prompt. Routes rebuild afterwards. SoundRouter also detects restarts it didn't start and rebuilds.
  • Rebuild all routes: tears down and recreates every tap and stream.
  • Match sample rates between an input and an output.
  • Device inspector: default output, input and sound-effects device; hardware volume and mute; sample rate; buffer size.
  • Export, import or reset the configuration. It's stored at ~/Library/Application Support/SoundRouter/config.json.

Architecture

Folder / fileResponsibility
App/AppState.swiftRoot model. Reacts to device and app events, runs rules and device priority, and converts the active profile into StreamSpecs (the planner). Handles fallbacks and alerts.
Audio/RouteEngine.swiftCompares the wanted streams with the running ones. Creates and destroys taps, private aggregate devices and IOProcs, and loads Audio Units.
Audio/ProcessTap.swiftWraps CATapDescription and AudioHardwareCreateProcessTap, plus aggregate-device creation.
Audio/DeviceManager.swiftDevice list, hot-plug and default-device listeners, volume, mute, sample rate, buffer size.
Audio/ProcessMonitor.swiftCore Audio process objects grouped by owning app (through the “responsible PID”), plus launch and quit events.
Audio/IOSDeviceEnabler.swiftThe CoreMediaIO switch that exposes iPad/iPhone audio.
DSP/*Real-time processing: StreamProcessor (render callback), EffectProcessor (lock-free parameter swap), biquad EQ, compressor, limiter, AURenderer (hosts Audio Units in the IOProc).
Model/Models.swiftCodable config: profiles, routes, rules, effects, settings.
Services/*Persistence, notifications, helper XPC client and launch registration, hot keys, volume keys, HUD.
UI/*SwiftUI views for the window and the menu bar.
Helper/main.swiftPrivileged daemon. It accepts XPC only from code signed with the same team ID and the app's bundle identifier.

How one app route works: SoundRouter creates a process tap on the app's processes with muteBehavior = .mutedWhenTapped, then a private aggregate device made of the target output plus the tap (drift-compensated). Its IOProc reads the tap's stereo channels, runs the effect stages, and writes to the output. An input route uses an aggregate of the input device (drift-compensated) and the output device.

Troubleshooting

SymptomTry
Routed app is silentCheck audio-capture permission. Look for an error under the app row. Then Tools › Rebuild routes.
iPad doesn't appearUnlock it, trust the Mac, try another cable or port, and toggle the switch off and on. As a last resort, click Enable in Audio MIDI Setup once; SoundRouter takes over from there.
Crackles in play-throughMatch sample rates and raise the buffer size slightly.
Helper says “requires approval”System Settings › General › Login Items & Extensions → allow SoundRouter.
Everything is stuckTools › Restart Core Audio, or quit SoundRouter. All apps return to normal output.

Project status

Builds; core routing tested. Both targets compile against the macOS 27 SDK (Xcode 27.1) with no errors or warnings. Per-app routing has been run end to end: the app starts a tap stream when a routed app plays, follows the app's processes as instances come and go, and stops when it quits. The UI, input routes, effects, rules and the helper haven't been exercised yet. The APIs that were most at risk, and how they turned out:
  • CATapDescription Swift names (isPrivate, processes as [AudioObjectID]) and updating a tap's process list in place through kAudioTapPropertyDescription. These names compile as written, and the in-place update works: the tap keeps its ID while processes are added and removed. It needs audio-capture permission; without it the HAL returns '!hog' and the engine falls back to rebuilding the stream.
  • AUAudioUnit.instantiate(with:options:) async form and .defaultLaunchBehavior on the window scene compile as written. requestViewController needed import CoreAudioKit.
  • Swift 5 language mode with @MainActor models. Switching to Swift 6 strict concurrency will need some Sendable annotations.

Ideas for later: per-app input routing (route an app's microphone), configurable shortcuts, a per-route latency readout, and a mixer view with outputs as columns.
